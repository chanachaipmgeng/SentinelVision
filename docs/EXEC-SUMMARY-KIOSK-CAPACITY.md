> **ตัวเลขและการแนะนำสเป็คล่าสุด (24 ก.ย. 2026):** ดูคู่มือรวม  
> **[KIOSK-CAPACITY-GUIDE.md](KIOSK-CAPACITY-GUIDE.md)**  
> — production = **quad · workers=3** · ลงเวลา ~**24–32 จอ** · Face Core BFF บนเครื่องนี้ยังไม่แนะนำสำหรับดัน concurrent

**วันที่วัดในไฟล์นี้ (บางส่วน):** 23 กันยายน 2026 (รอบ saturation / dual-API) — อาจต่ำกว่าเพดานรอบหลัง

## 1. โปรดักต์นี้ทำอะไร

ระบบลงเวลาทำงานด้วยการจดจำใบหน้า:

1. พนักงานยืนหน้ากล้องที่ **จอคีออส** (ไม่ต้องแตะเครื่อง)
2. ระบบตรวจจับใบหน้า → จับคู่กับข้อมูลที่ลงทะเบียนไว้ → บันทึกเวลาเข้า/ออก
3. แอดมินจัดการบริษัท พนักงาน สถานที่ และนำเข้าข้อมูลผ่านเว็บ

คอขวดหลักของความเร็วอยู่ที่ **การประมวลผลใบหน้าบนการ์ดจอ (GPU)** ของเซิร์ฟเวอร์

---

## 2. สเป็คที่ทดสอบ (รอบล่าสุด)

| รายการ | ค่าที่ใช้ทดสอบ |
|--------|----------------|
| เซิร์ฟเวอร์ | production (`10.50.0.117`) |
| การ์ดจอ (GPU) | **2 ใบ** · Quadro RTX 5000 · 16 GB/ใบ |
| สถาปัตยกรรม | **API 2 process** แยกตาม GPU (nginx กระจายโหลด) · คนละ 2 workers |
| วิธีวัด | จำลองจอคีออสหลายจอ · เฟรมขนาดใกล้ของจริง (~1280 px, JPEG q70) |
| เกณฑ์คุณภาพ (UX) | กรอบใบหน้า ≤ ~0.55 วินาที · ทิ้งเฟรม ≤ 5% |

> รอบก่อนใช้ process เดียว + เฟรมทดสอบใหญ่เกินจริง ทำให้ตัวเลข **conservative** (ต่ำกว่าความจุจริง)

## 3. สรุปผลในหนึ่งหน้า

### คำตอบสั้น ๆ สำหรับวางแผนติดตั้ง

| สถานการณ์หน้างาน | รอบ 3 (ล่าสุด, 4 process) | รอบ 2 (2 process) | รอบ dual-API | รอบก่อน |
|------------------|---------------------------|-------------------|--------------|---------|
| เร่งด่วนหนาแน่น (~หลายคนในกล้อง) | **ไม่เกิน 24 จอ** | 16 จอ | 6 จอ | 4–5 จอ |
| เร่งด่วนคนละคนต่อจอ | **ไม่เกิน 32 จอ** | 24 จอ | 12 จอ | 8 จอ |
| ช่วงโล่ง / กล้องรอคน | **≥ 48 จอ** (ยังไม่ชนเพดาน) | ≥ 32 จอ | 24 จอ | 12 จอ |

### ภาพรวมความจุ (หลังปรับรอบ 3)

```
เร่งด่วนหนาแน่น     ████████████████████████░░░░░░░░ ~24 จอ   ← ใช้วางแผน deploy จริง
เร่งด่วนคนละคน/จอ   ████████████████████████████████ ~32 จอ
ช่วงโล่ง (detect)   ████████████████████████████████████████████████ ≥48 จอ
```

### สิ่งที่พิสูจน์แล้วจากการวัดรอบนี้

- การ์ดจอ **ทั้ง 2 ใบมี process ของระบบจริง** (~2 GB/ใบ)
- แยก API ตาม GPU + แก้การ pin อุปกรณ์ แล้ว GPU1 ไม่ถูกทิ้งว่างเหมือนรอบก่อน
- รอบ 2 (ลดงานต่อคำขอ: ตรวจจับที่ 320 px แล้วจดจำทันที, ไม่เขียนไฟล์ชั่วคราว, worker 3 ต่อ process) ทำให้เพดานชั่วโมงเร่งด่วน **เพิ่มจาก 6 → 16 จอ** โดยไม่แตะฮาร์ดแวร์
- รอบ 3 (API 2 process ต่อการ์ด = 4 process ใช้ CPU 32 core ที่ว่างอยู่ + ย้ายบริการถอดเสียง whisper ออกจาก GPU0) เพดานเร่งด่วน **16 → 24 จอ**, คนละคนต่อจอ **24 → 32 จอ**
- ตัวเลขนี้วัดด้วยโหลดที่หนักกว่าจริง (จอส่งภาพ 11 เฟรม/วินาทีตลอด) — หน้าบ้านรอบ 2 ส่งน้อยลงเมื่อคนยืนนิ่ง จอจริงจึงรับได้มากกว่านี้
- ยังไม่จำเป็นต้องแยก Face Core แค่เพื่อ “ใช้ GPU ให้เต็ม” บนเครื่องนี้ (GPU ยังใช้เฉลี่ย ~11%)

## 4. แปลผลเป็นภาษาธุรกิจ

| คำถามของผู้บริหาร | คำตอบจากผลการทดสอบล่าสุด |
|-------------------|---------------------------|
| ติดตั้งกี่จอต่อเซิร์ฟเวอร์นี้ได้โดยยังลื่น? | **24 จอ** สำหรับชั่วโมงเร่งด่วนที่มีคนหนาแน่น |
| ถ้าส่วนใหญ่คนละคนต่อจอ? | ได้ถึงประมาณ **32 จอ** |
| เกินแล้วเกิดอะไรขึ้น? | ภาพช้า กรอบกระพริบ ทิ้งเฟรมสูง — ระบบยังลงเวลาได้แต่ UX แย่ |
| ถ้าต้องการมากกว่า 32–48 จอ? | GPU ยังใช้แค่ ~16% — เพิ่ม process ต่อการ์ดได้อีก แต่ผลตอบแทนเริ่มลด; ถัดจากนั้นคือสเกลข้ามเครื่อง (Face Core) หรือแยก DB |

---

## 5. ข้อเสนอแนะเชิงปฏิบัติ

1. **เพดานติดตั้งแนะนำ = 24 จอ** สำหรับการใช้งานจริงแบบหนาแน่นบนเซิร์ฟเวอร์นี้ (เผื่อ margin ใช้ 16–20)
2. โซนที่คนส่วนใหญ่ยืนคนละจอ: วางแผนได้ถึง **32 จอ**
3. **ยังไม่ต้องลงทุนแยก Face Core** เพื่อเพิ่มความจุบนเครื่องใบนี้ — งานนั้นเหมาะตอนสเกลหลายเครื่อง
4. เก็บเกณฑ์ UX: ตอบสนองกรอบ ≤ ~0.55 วินาที · ทิ้งเฟรม ≤ 5% ในชั่วโมงเร่งด่วน

---

## 6. สรุปหนึ่งประโยค

**หลังปรับรอบ 3 (ใช้ GPU สองใบจริง + ลดงานต่อคำขอ + API 4 process) เซิร์ฟเวอร์ Quadro RTX 5000 สองใบนี้รองรับจอคีออสได้อย่างลื่นประมาณ 24 จอในช่วงเร่งด่วนหนาแน่น และราว 32 จอถ้าโดยทั่วไปมีคนละคนต่อจอ — เพิ่มจากจุดเริ่มต้น ~4 เท่าโดยไม่ซื้อฮาร์ดแวร์เพิ่ม**
