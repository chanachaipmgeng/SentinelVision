DPU Attendance / Face-in — ระบบลงเวลาด้วยใบหน้า

เวอร์ชันเอกสาร: 1.0  |  วันที่: 18 กันยายน 2026
ผู้ใช้งาน: myHR (face-in.myhr.co.th)
โหมดที่ติดตั้งจริง: InsightFace ในเครื่อง (FACE_CORE_ENABLED=false) + GPU

ตัวเลขความจุและ concurrent เป็นค่าประมาณจากสถาปัตยกรรมปัจจุบัน ยังไม่ได้ทำ load test เต็มระบบบนเซิร์ฟเวอร์นี้

1. ภาพรวม

ระบบลงเวลาเข้า–ออกงานด้วยใบหน้าสำหรับหลายบริษัท แอดมินจัดการพนักงานและลงทะเบียนใบหน้า พนักงานลงเวลาที่คีออสในเว็บแอดมิน ไม่มีแอปมือถือแยก

  • จดจำใบหน้า: InsightFace รุ่น buffalo_l (embedding 512 มิติ)
  • ค้นหา 1:N ภายในบริษัทเท่านั้น ไม่ค้นข้ามบริษัท
  • เก็บ vector ใน PostgreSQL + ส่วนขยาย pgvector (ดัชนี HNSW, cosine)
  • กันลงเวลาซ้ำด้วยช่วงเวลา (ค่าเริ่มต้น 5 นาที)
  • ตรวจพิกัดสถานที่ (geofence) ตอนบันทึกลงเวลา

2. สถาปัตยกรรม (โหมดที่ใช้อยู่)

Docker Compose หลัง nginx — โค้ดถูก bake ใน image ต้อง rebuild หลังแก้ซอร์ส

บริการบทบาท
dpu-nginxเกตเวย์พอร์ต HTTP อัปโหลดได้ถึง 500 MB, import timeout 1 ชั่วโมง, WebSocket คีออส
dpu-adminAngular 17 หน้าแอดมิน + คีออส /company/timestamp-face
dpu-apiFastAPI + InsightFace + คิว GPU
dpu-dbPostgreSQL 16 + pgvector

เส้นทางข้อมูล: เบราว์เซอร์ → nginx → admin (หน้าเว็บ) หรือ api (ใบหน้า / HR) → Postgres

FACE_CORE_ENABLED เป็นสวิตช์ส่งงานวิชันไปบริการ face-core แยก
เซิร์ฟเวอร์นี้ตั้ง false ไม่จำเป็นต้องมี face-core

4. สเป็คฮาร์ดแวร์ที่ตรวจบนเซิร์ฟเวอร์

รายการที่พบบนเครื่อง myhr
GPUNVIDIA Quadro RTX 5000 จำนวน 2 ใบ (VRAM 16 GB/ใบ)
ไดรเวอร์ที่ต้องตรงกันเคอร์เนลโมดูลกับ NVML ต้องเป็นรุ่นเดียวกัน (เช่น 580.178)
GPU ที่ระบบใช้ตอนนี้cuda:0 ใบเดียว (ใบที่สองยังไม่ถูกใช้)
NVIDIA persistencedต้องมี /run/nvidia-persistenced/socket เพื่อให้คอนเทนเนอร์ GPU ขึ้น
บน nvidia-smi พบคำเตือน infoROM corrupted ทั้งสองใบ ไม่ได้บล็อกการรัน แต่ควรสำรองและติดตามสุขภาพ GPU

5. ความจุจำนวนคน (gallery)

ค้นหาใบหน้าจำกัดต่อบริษัท + ดัชนี HNSW — embedding ในเบสเล็กมาก (~2 KB/คน) จุดที่โตคือไฟล์ JPEG

ระดับจำนวนโดยประมาณหมายเหตุ
ใช้งานสบาย2,500 – 10,000 คน / บริษัทตรงกับชุด import หลักพัน–หมื่น
ยังรองรับ~20,000 – 50,000 คนค้นหายังเร็ว ดิสก์รูปจะโตก่อน CPU
ต้องออกแบบใหม่แสนคนขึ้นไป หรือค้นข้ามทุกบริษัทไม่ใช่โหมดปัจจุบันของระบบ

ประมาณการดิสก์รูป: หลักสิบ–ร้อย KB ต่อไฟล์ × 2 ชุด (โปรไฟล์ + ใบหน้าที่ลงทะเบียน)

6. Concurrent (ใช้งานพร้อมกัน)

คอขวดคือคิว GPU ไม่ใช่หน้าเว็บแอดมิน

พารามิเตอร์ค่าเริ่มต้น
FACE_GPU_WORKERS1 (ประมวลผลใบหน้าทีละงาน)
FACE_GPU_QUEUE_SIZE64 (คิวรอสูงสุด)
Throughput โดยประมาณบน RTX 5000ประมาณ 5–10 งานใบหน้า / วินาที
สถานการณ์ความเหมาะสม
คีออส 1 จอ คนเดินผ่านเป็นกลุ่มรองรับดี
คีออส 2–4 จอ พร้อมกันยังไหว เริ่มมีงานรอในคิว
คีออส 10+ จอ หรือคนอัดหน้ากล้องพร้อมกันมากหน่วง งานรอเต็มคิว 64
แอดมินเปิดเว็บพร้อมกันหลายสิบคนไม่ใช่คอขวด
Import Excel+ZIP หลักพันรูปรันทีละรูปบน GPU ใช้เวลาหลายนาที

ตรวจคิวจริง: GET /face/queue-stats ดู pending / active / workers

7. คีออสลงเวลา

  • เส้นทาง: /company/timestamp-face (เต็มจอ ไม่มีแอปมือถือแยก)
  • โหมดหลัก: WebSocket /face/ws/kiosk (identify + walk-by check-in)
  • สำรอง: HTTP walk-by หาก WS ใช้ไม่ได้
  • หลายคนในเฟรม: ติดตามด้วย IoU ส่งครอปใบหน้า ไม่ล็อกกล้องทั้งจอให้คนเดียว
  • ค้นหาและลงเวลาต้องส่ง companyId — ไม่จับคู่ข้ามบริษัท
  • กันลงเวลาซ้ำ: CHECK_IN_DEDUPE_SECONDS (ค่าเริ่มต้น 300 วินาที)

11. ข้อแนะนำเมื่อจะขยาย

  • เพิ่มคีออสพร้อมกันหลายจุด: ตั้ง FACE_GPU_WORKERS และใช้ GPU ใบที่สอง หรือแยกวิชันไป Face Core
  • ไดรเวอร์ NVIDIA หลังอัปเดตต้องรีบูต ให้เคอร์เนลโมดูลตรงกับ NVML
  • อัปโหลดผ่าน HTTPS ต้องตั้งขนาดบอดี้ที่ nginx ฝั่ง TLS ไม่ใช่แค่ใน Docker
  • หลังแก้โค้ด API/UI/nginx ต้อง rebuild image ที่เกี่ยวข้อง
