ความจุระบบลงเวลาด้วยใบหน้า (Face Kiosk)

อัปเดต: 24 กันยายน 2026 · เซิร์ฟเวอร์วัด: face-in (10.50.0.117) · ฮาร์ดแวร์: CPU 32 คอร์ · RAM ~436 GB · GPU 2× Quadro RTX 5000 (16 GB)

1. เราตัดสิน “ดี/ไม่ดี” ยังไง

ทีมเทสใช้เกณฑ์คุณภาพเดียวกับที่ผู้ใช้รู้สึกได้:

  • ความเร็ว: 95% ของคำขอ (p95) ต้องไม่ช้าเกิน 550 มิลลิวินาที
  • ความนิ่ง: ทิ้งเฟรม (drop) ไม่เกิน 5%
  • ตัวเลขด้านล่างคือค่าที่ วัดบนเซิร์ฟเวอร์จริง ไม่ใช่ประมาณการจากสเป็คการ์ดอย่างเดียว

2. วิธีไหนดีที่สุด — เปรียบเทียบแบบภาษาพูด

วิธี พูดสั้น ๆ ผลที่วัดได้ ควรใช้ไหม
DPU Monolith · Quad (4 process) ประมวลผลใบหน้าอยู่ใน API เอง แยก 4 โปรเซสใช้ GPU คู่ ลงเวลาได้ 24–32 จอ · หาชื่ออย่างเดียวสูงกว่านี้ได้ถ้าขยายชั่วคราว แนะนำ — ใช้เป็น production
DPU Monolith · Hexa (6 process) เพิ่ม process เพื่อดันหาชื่อให้เยอะขึ้น หาชื่อได้สูงถึง ~64–80 จอ แต่ลงเวลาแย่ลงถ้าเปิดถาวร ใช้ชั่วคราวเฉพาะโหมดโชว์ชื่อ
Face Core แยกบริการ (BFF) แยกบริการ vision ออกจาก DPU ส่งงานผ่านเครือข่าย/HTTP จูนเต็มที่แล้วยังได้แค่ประมาณ ≤ 2 จอ ภายใต้เกณฑ์ความเร็ว ยังไม่ใช้เพื่อเพิ่มจำนวนจอบนเครื่องนี้
ทำไมไม่เลือก Face Core ตอนนี้: ไม่ใช่เพราะยังจูนไม่ครบ — จูนคิว / worker / ปัก GPU แล้ว — แต่สถาปัตยกรรม 2 โปรเซสของ Core ไล่ความจุของ Monolith 4–6 โปรเซสไม่ทันบนฮาร์ดแวร์ชุดนี้ เหมาะกับงานแยกทีม/หลายโฮสต์ในอนาคต มากกว่าการดันจำนวนคีออสบนเครื่องเดียว

3. ค่าที่ทดสอบได้จริง (ตัวเลขสำคัญ)

3.1 ลงเวลาและจำนวนจอพร้อมกัน

3.2 ช่วงเช้า / เร่งด่วน — “สแกนได้กี่หมื่นใน 20 นาที”

วัดด้วยการเปิดจอพร้อมกัน ยิงหาชื่อแบบหน่วงใกล้จอจริง (ทุก ~600 ms) นาน 20 นาที:

จำนวนจอหาชื่อสำเร็จใน 20 นาทีเฉลี่ยต่อนาทีความเร็ว p95ผล
24 จอ17,998 ครั้ง~900211 msผ่าน
32 จอ22,783 ครั้ง~1,139228 msผ่าน

แปลเป็นภาษาธุรกิจ: ถ้าสาขาเปิดคีออส 24–32 จอพร้อมกันในช่วงเช้า ระบบชุดนี้รองรับการ “รู้ว่าเป็นใคร” ได้ราว หนึ่งจุดแปดถึงสองจุดสามหมื่นครั้ง ใน 20 นาที โดยยังเร็วกว่าเกณฑ์คุณภาพมาก

3.3 ลงเวลา (check-in) — ข้อควรเข้าใจ

  • ระบบมี กันลงซ้ำ ~5 นาที ต่อคน (ปกติในโปรดักชัน) — กันพนักงานกด/สแกนรัว ๆ
  • ถ้าเทสด้วยใบหน้าเดิมซ้ำ ๆ ตัวเลข “ลงเวลาใหม่” จะต่ำทั้งที่ระบบยังทำงานเร็ว
  • เมื่อจำลองคนละสมาชิก / ปิดกันซ้ำชั่วคราวเพื่อวัดท่อระบบ ที่ 24 จอ · 10 นาที ได้ check-in สำเร็จราว 21,000 ครั้ง (p95 ~209 ms)

ดังนั้นเวลาคุยความจุช่วงเช้ากับผู้บริหาร แนะนำใช้ตัวเลข หาชื่อสำเร็จต่อช่วงเวลา เป็นหลัก จะสื่อความหมาย “รองรับคิวคนเช้า” ได้ตรงกว่า

3.4 ฐานข้อมูลใบหน้าใหญ่แค่ไหนถึงมีปัญหา

ขนาดแกลเลอรีโดยประมาณความเร็วหาชื่อ (p95) ที่ 16 จอผล
~10,000 ใบหน้า207 msผ่าน
~20,000 ใบหน้า155 msผ่าน
~35,000 ใบหน้า174 msผ่าน

สรุป: บริษัทที่มีพนักงานหลักหมื่นคน (ถึงราว 3.5 หมื่นใบหน้า) ยังไม่ใช่คอขวด บนเครื่องนี้ — สิ่งที่จำกัดมากกว่าคือ จำนวนจอที่เปิดพร้อมกัน

3.5 หลายบริษัทบนเครื่องเดียว

เทสเปรียบเทียบ “20 จอของบริษัทเดียว” กับ “20 บริษัท ๆ ละ 1 จอ” (จอรวมเท่ากัน):

  • ทั้งสองแบบผ่านเกณฑ์ความเร็ว
  • แยกหลายบริษัทไม่ได้เพิ่มเพดานจำนวนจอ — แค่กระจายโหลด
  • วางแผนติดตั้งให้คิดจาก จอสูงสุดพร้อมกันทั้งเครื่อง ไม่ใช่จำนวนบริษัท

3.6 เทสเสริม (Spike / Soak / Vector / เน็ต) — สรุปสั้น

  • Spike HTTP identify: ดัน concurrency สูงได้ peak ประมาณ ~23 รูป/วินาที · ช้าเกิน 1–2 วินาทีตั้งแต่หลักสิบ concurrent · มี HTTP 502 บ้างที่โหลดสูง · ไม่พบ 504 และ DB connection ไม่ชนเพดาน
  • Soak 2 ชั่วโมง: RAM คอนเทนเนอร์ API ไม่โตสะสม · GPU ทั้งสองใบมี VRAM ค้างใช้งาน
  • ค้นหา 20,000 ใบหน้า: ยิงค้นหาพร้อมกันหลักร้อย–ห้าร้อย รายการยังจบในระดับร้อยมิลลิวินาที (p95) · เขียนพร้อมอ่านไม่ทำให้ค้างล็อก
  • แบนด์วิดท์: 24–32 จอส่งเฟรมรวมราว 40–52 Mbps — ไม่น่าเป็นคอขวดบน LAN ปกติ
ยังไม่ต้องจูนค่าเซิร์ฟเวอร์เพิ่มจากรอบนี้ — ไม่มีหลักฐานว่าต้องขยาย DB pool หรือปรับดัชนีเวกเตอร์เพื่อดันความจุคีออส

5. ข้อแนะนำเชิงธุรกิจ / ปฏิบัติการ

  1. เปิดสาขาใหม่: วางแผนคีออสลงเวลาที่ 24 จอต่อเครื่องนี้ เป็นค่าเริ่ม · ขึ้นได้ถึง ~32 ถ้าโปรไฟล์ใช้งานเป็นคนเดียวต่อจอและวัดซ้ำได้
  2. ช่วงเช้าคนแน่น: ตรวจว่า process ครบ 4 · GPU ทั้งสองใบมีงาน · อย่าสลับไป Hexa เพราะอยากได้จอโชว์ชื่อแล้วลืมวัดลงเวลา
  3. บริษัทใหญ่ / ใบหน้าเยอะ: ระดับหมื่นถึง ~3.5 หมื่นใบหน้าต่อบริษัทยังโอเค — โฟกัสที่จำนวนจอ peak มากกว่า
  4. หลายบริษัท: นับจากจอรวมสูงสุดของทั้งเครื่อง ไม่ใช่จำนวนบริษัท
  5. อยากได้ความจุสูงกว่านี้: ต้องเพิ่มฮาร์ดแวร์ (GPU/โหนด) หรือลดโหลดฝั่งจอ — จูนค่า env ซ้ำบนเครื่องนี้ได้ผลจำกัดแล้ว
  6. Face Core: คงไว้สำหรับทดลองแยกบริการในอนาคต · อย่าคาดหวังให้เพิ่มจำนวนจอบนเซิร์ฟเวอร์นี้เกิน Monolith
