นิยามโปรไฟล์ทดสอบ (จำลองพฤติกรรมคีออสจริงจาก `enroll-face.component.ts`):

- **idle** — จอมีคนอยู่ในเฟรมแต่ไม่ลงเวลา: ส่ง detect ทุก 90 ms ต่อเนื่อง (~11 เฟรม/วินาที/จอ)
- **rush × 3** — 3 คนหน้ากล้องพร้อมกัน: detect + identify (≤ 2 ค้าง) + check-in (≤ 3 ค้าง) ตลอด 30 วินาที

เกณฑ์ผ่าน (SLO): **detect p95 ≤ 550 ms · ทิ้งเฟรม ≤ 5% · session p95 ≤ 500 ms** — ตัวเลข "ใช้ได้" ในรายงานคือจำนวนจอสูงสุดที่ยังผ่านเกณฑ์นี้

> ตัวเลขทั้งหมดวัดด้วยโหลดที่ **หนักกว่าจริง**: loadgen ส่ง detect เต็มอัตราตลอด ไม่มี cooldown 5 นาทีหลังลงเวลา และไม่มี motion gating ของหน้าบ้าน — ของจริงจึงรับได้มากกว่านี้

## 4. สาเหตุที่ระบบช้า (จากหลักฐานที่วัด ไม่ใช่การเดา)

| ลำดับ | คอขวด | หลักฐาน | สิ่งที่แก้แล้ว |
|-------|-------|---------|----------------|
| 1 | **CPU/GIL ใน Python process เดียว** — decode JPEG, base64, JSON, WebSocket I/O แย่ง GIL กับ ONNX | process เดียว: GPU ว่าง 80%+ แต่ worker "ยุ่ง" ตลอด; แยก 2 process แล้วเพดาน idle 12 → 24 จอ; 4 process → ≥48 | Dual API (รอบ dual) → Quad API (รอบ 3) |
| 2 | **GPU1 ไม่ถูกใช้จริง** — insightface ไม่ส่ง `device_id` ให้ CUDA provider ทำให้ทั้ง `cuda:0` และ `cuda:1` ลง GPU0 | `nvidia-smi --query-compute-apps` เห็น python เฉพาะ GPU0 | ส่ง `provider_options device_id` + `CUDA_VISIBLE_DEVICES` ต่อ process |
| 3 | **หน้าบ้านส่งเฟรมถี่เกินจำเป็น** — 11 เฟรม/วินาที/จอ แม้ภาพนิ่ง | idle 24 จอ = ~264 detect/วินาที คือโหลดหลัก | thumbnail diff + ปรับ interval ตามสถานะ track (รอบ 2) |
| 4 | **path identify/check-in เขียนไฟล์ + detect ซ้ำที่ 640** — เขียน temp → อ่านซ้ำ → detect 640 → embed → copy รูป | identify p95 300–700 ms ใน rush แม้ detect ยังดี | ทำใน memory + det@320 แล้ว embed จาก keypoints (รอบ 2) |
| 5 | **เฟรมทดสอบใหญ่เกินจริง** (~546 KB / 3,936 px) ทำให้ตัวเลขแย่กว่าจริง | decode 3.7 MP กิน CPU 15–25 ms/เฟรม | loadgen ใช้เฟรม 1280 px q70 (~78 KB) เท่าคีออสจริง |
| 6 | **GPU0 ถูกแชร์กับ whisper_server** (~4 GB) | compute-apps บน GPU0 | ย้ายไป GPU1 (รอบ 3) — ผลต่อ latency น้อย เพราะ GPU ไม่ใช่คอขวด |

## 5. ข้อแนะนำที่จำเป็น

### 5.1 การติดตั้งใช้งานจริงบนเซิร์ฟเวอร์นี้

1. **วางแผนติดตั้งไม่เกิน 16–20 จอ** ในโซนที่ชั่วโมงเร่งด่วนมีหลายคนหน้ากล้อง (เพดานเทส 24)
2. โซนที่คนละคนต่อจอ / มือถือส่วนตัว: **ไม่เกิน 24–28 คนพร้อมกัน** (เพดานเทส 32)
3. ใช้ overlay **quad-API** ตาม `docs/DEPLOY-SERVER.md` (`docker-compose.gpu.yml` + `docker-compose.gpu-x2.yml`) และคง `FACE_GPU_WORKERS=3`
4. เก็บเกณฑ์ UX: กรอบตอบสนอง ≤ 0.55 วินาที · ทิ้งเฟรม ≤ 5% — ถ้าเกินให้ลดจำนวนจอหรือขยายตาม §7
5. `whisper_server` ไม่อยู่ใน systemd — หลังรีบูตต้องรันใหม่พร้อม `CUDA_VISIBLE_DEVICES=1` (บันทึกใน DEPLOY-SERVER)

### 5.2 การปรับปรุงลำดับถัดไป (เรียงตามผลตอบแทน)

| ลำดับ | รายการ | คาดผล | ความยาก |
|-------|--------|-------|---------|
| 1 | **ลดงาน DB ต่อ check-in** — cache dedupe ใน memory ต่อ process (TTL 5 นาที) ก่อน query, เขียน timestamp แบบ async batch | check-in p95 ลด 30–50% ใน rush | ต่ำ–กลาง |
| 2 | **3 process ต่อ GPU** (6 process) บนเครื่อง 32 core | rush×3 24 → ~32 จอ (ผลตอบแทนเริ่มลด) | ต่ำ (compose overlay) |
| 3 | **วัดด้วยคีออสจริง** (motion gating ทำงาน) แทน loadgen เต็มอัตรา | ได้ตัวเลขจริงที่สูงกว่าตาราง | ต่ำ |
| 4 | **แยก DB ออกจากเครื่อง API** เมื่อเกิน ~40 จอ | ตัด contention CPU/IO ระหว่าง API กับ Postgres | กลาง |
| 5 | **Face Core หลายเครื่อง + Redis queue** | สเกลเป็นร้อยจอ / หลายบริษัท | สูง — ทำเมื่อต้องข้ามเครื่องเท่านั้น |

### 5.3 สิ่งที่ไม่ควรทำ

- ไม่ต้องซื้อ GPU เพิ่มเพื่อเครื่องนี้ — GPU ใช้เพียง ~16%
- ไม่ต้องเพิ่ม `FACE_GPU_WORKERS` เกิน 3 — A/B 2 vs 3 ไม่ต่างในระดับ noise; เกินนี้จะแย่ง GPU กันเอง
- ไม่ต้องแยก Face Core เพื่อ "ใช้ GPU ให้เต็ม" — ปัญหาอยู่ที่ CPU/DB ไม่ใช่ GPU

## 6. การประมาณสเป็ค — เครื่องเดียว

หลักคิด: **1 API process ≈ 1.2–1.5 CPU core เมื่อเต็มโหลด** และรับ rush ได้ประมาณ **6–8 จอ (3 คน/จอ)** หรือ **8–10 คน (คนละคน/จอ)**; GPU 1 ใบรองรับได้ 2–3 process โดยยังใช้ SM ไม่ถึง 40%

| เป้าหมายพร้อมกัน (rush) | API process | CPU core แนะนำ | RAM | GPU | หมายเหตุ |
|--------------------------|-------------|----------------|-----|-----|----------|
| ≤ 6 จอ / ≤ 12 คน | 1 | 4–8 | 16 GB | 1 ใบ ระดับ RTX 4060 / T4 | เครื่องเล็ก / สาขา |
| ≤ 16 จอ / ≤ 24 คน | 2 (1/GPU) | 8–16 | 32 GB | 1–2 ใบ | ค่าที่วัดได้รอบ 2 |
| **≤ 24 จอ / ≤ 32 คน** | **4 (2/GPU)** | **16–32** | 32–64 GB | **2 ใบ RTX 5000** | **เครื่องปัจจุบัน (รอบ 3)** |
| ≤ 32 จอ / ≤ 48 คน | 6 (3/GPU) + DB แยก | 32 | 64 GB | 2 ใบ | ประมาณการ — ยังไม่ได้วัด |
| > 48 จอ / > 64 คน | หลายเครื่อง | — | — | — | ดู §7 |

การ์ดจอ: งานเป็น RetinaFace 320 + ArcFace r50 ที่ ~5–15 ms/งาน — การ์ดระดับ 8–16 GB ทั่วไปเพียงพอ; **จำนวน CPU core และ process สำคัญกว่า GPU รุ่นแรง**

## 7. การประมาณสเป็ค — กรณี 10,000 คนลงเวลาช่วงเดียวกัน

### 7.1 แปลงเป็นอัตราคำขอ

| สมมติฐาน | ค่า |
|----------|-----|
| พนักงาน | 10,000 คน |
| หน้าต่างเวลาลงเวลา | 20 นาที (07:50–08:10) |
| อัตราเฉลี่ย | ≈ **8.3 คน/วินาที** |
| อัตราพีค (นาทีที่แน่นสุด ~3–5× ของเฉลี่ย) | ≈ **25–45 คน/วินาที** |
| งานต่อ 1 คน (คีออสจริงหลัง motion gating) | detect ~15–25 เฟรม + identify 1–2 + check-in 1 ≈ 20–30 คำขอ |
| คำขอรวมช่วงพีค | ≈ **600–1,200 คำขอ/วินาที** |

### 7.2 เครื่องปัจจุบันรับได้เท่าไร

จากรอบ 3: 24 จอ rush×3 = ~72 คนหน้ากล้องพร้อมกัน ≈ **50–60 detect/วินาที + ~35 identify/วินาที + ~95 check-in/วินาที** โดยยังผ่าน SLO → เทียบเป็น **"ลงเวลาสำเร็จ" ประมาณ 3–6 คน/วินาที** ต่อเครื่อง (ขึ้นกับเวลาที่แต่ละคนยืนหน้ากล้อง ~4–8 วินาที)

**ดังนั้น 1 เครื่อง ≈ 4,000–7,000 คนต่อ 20 นาที ถ้าโหลดกระจายสม่ำเสมอ — แต่ที่พีค 25–45 คน/วินาที จะล้นทันที**

### 7.3 สเป็คที่แนะนำสำหรับ 10,000 คน / 20 นาที

| องค์ประกอบ | จำนวน / สเป็ค | เหตุผล |
|------------|---------------|--------|
| **จอ/จุดลงเวลา** | **≥ 120–150 จุด** (คนละคนต่อจอ) หรือ ≥ 60 จอแบบหลายคน | 45 คน/วินาที × 4–6 วินาที/คน ≈ 180–270 คนยืนพร้อมกันตอนพีค — จำนวนจอเป็นข้อจำกัดทางกายภาพก่อนซอฟต์แวร์ |
| **API/Face node** | **4–6 เครื่อง** ระดับเครื่องปัจจุบัน (16–32 core, 2 GPU 16 GB) หรือ 8–12 เครื่องระดับ 1 GPU | แต่ละเครื่องรับ ~30 คนพร้อมกัน / ~5 ลงเวลาต่อวินาที; ต้องการ ~250 คนพร้อมกันตอนพีค + margin 30% |
| **Load balancer** | nginx / HAProxy `least_conn` แยกเครื่อง, sticky ต่อ WebSocket | กระจาย WS ต่อ connection |
| **Database** | PostgreSQL + pgvector แยกเครื่อง: 16 core, 64 GB, NVMe; connection pool รวม ≥ 300; พิจารณา read replica สำหรับ 1:N search | check-in insert ~50–100/วินาที + dedupe query + vector search 10,000 embedding (×5 มุม) |
| **Object storage** | NFS/S3 สำหรับรูป punch (~50 KB × 10,000 = ~500 MB/วัน) | หลาย node ต้องเขียนรูปที่เดียว |
| **Queue (ทางเลือก)** | Face Core + Redis เมื่อต้องการ fairness หลายบริษัท | ไม่จำเป็นถ้าแยก node ตามสาขา/บริษัทอยู่แล้ว |

### 7.4 ทางเลือกลดสเป็ค (ทำได้ทันที ไม่ต้องซื้อ)

- **กระจายเวลา:** แบ่งกะ/แผนกลงเวลาต่างช่วง 10–15 นาที ลดพีคจาก 45 → ~15 คน/วินาที → ลดจำนวนเครื่องลงครึ่งหนึ่ง
- **แยกตามสาขา:** สาขาละเครื่อง (แต่ละสาขาไม่น่ามี > 1,000 คนลงเวลาพร้อมกัน) แล้ว sync ไปฐานกลาง
- **ลดงานต่อคน:** motion gating (มีแล้ว) + cooldown 5 นาที (มีแล้ว) + ทำ dedupe cache ใน memory (ข้อแนะนำ §5.2-1)

**คำตอบตรง ๆ:** 10,000 คนในช่วงเดียวกัน **ทำได้** แต่ต้องเป็นระบบ **4–6 เครื่องระดับปัจจุบัน + DB แยก + จุดลงเวลา ≥ 120** — ไม่ใช่เครื่องเดียว
